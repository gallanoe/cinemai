# Video prompting for CinemAI

`generate_video` posts to OpenRouter's async video endpoint. A clip takes minutes and costs
in dollars rather than cents, so the cost of a bad prompt is much higher here than for
images. Two facts shape everything below.

## Two things that make this harder than image prompting

**You cannot see the result.** There is deliberately no video equivalent of `view_image` —
a clip cannot be loaded into your context. The user watches it in the widget; you never do.
So the verification loop that rescues a mediocre image prompt does not exist. You get one
description of what happened, from the user, minutes later.

**Every clip is an audio clip whether you asked or not.** `generate_audio` defaults to
**true** upstream on Seedance, so omitting it means the model invents a soundtrack — and
generated audio is screened for **copyright** *after* generation. A prompt that passes input
screening can still be rejected once the audio is sampled, after you have paid for the
render. If the clip does not need diegetic sound, **pass `generate_audio: false`
explicitly.** That removes an entire class of paid-then-rejected failure.

## The parameter surface

```
prompt  model  duration  resolution  aspect_ratio  seed
generate_audio  input_references  reference_mode
```

`reference_mode` decides how references are used: `first_frame` (default) pins the opening
frame, `last_frame` pins the closing one, `style` passes them as loose guidance. The first
two send `frame_images`; `style` sends `input_references`. Only one is ever sent.

**Not exposed by this server**, though the providers accept them: Seedance's `watermark` and
`req_key`, and Veo's `negativePrompt`, `enhancePrompt`, `personGeneration`,
`conditioningScale`. So there is **no negative-prompt field on any model here** — exclusions
go in the prompt text. Seedance's `duration: -1` (model picks the length) is also unreachable,
which is just as well: it is a billing risk, since the model may choose 15s.

**A 10-minute ceiling.** `VIDEO_POLL_TIMEOUT_MS` marks a job failed after 10 minutes. A
480p clip measured ~136s; Seedance 4K is reported at 4–8 minutes. That is real but thin
headroom — at the top of the range a job can be marked failed while upstream is still working.

## Cost, which you can compute exactly

Seedance bills per **video token**, not per second, and BytePlus documents the formula:

```
tokens = (width × height × fps × duration) / 1024      at 24 fps
```

That predicts a measured `seedance-2.0-fast` 4s/480p clip at **$0.21504** against an actual
**$0.2152** — 0.07% off, so treat it as reliable. Per second:

| | `seedance-2.0` | `seedance-2.0-fast` |
|---|---|---|
| 480p | $0.067/s | $0.054/s |
| 720p | $0.151/s | $0.121/s |
| 1080p | $0.340/s | — (not supported) |
| 4K | $1.361/s | — |

Two consequences worth internalising. **Aspect ratio is free** — the pixel budget is held
constant, so a 21:9 clip costs exactly what 16:9 costs. And **4K is a trap on Seedance**: the
model's native resolution is 480p/720p, so 1080p and 4K are upscales, and 8s of 4K runs about
**$10.89** versus roughly $0.64 for the same thing on `google/veo-3.1-lite`. If you genuinely
need 4K, use Veo; if you need Seedance's motion, render at 720p and upscale in post.

Draft at **480p** and commit at 720p. A 5s draft costs about **$0.27**.

## Seedance 2.0's published formula

ByteDance publishes this verbatim, and it is worth following because the rationale is
mechanical rather than stylistic — the model decomposes input into a "spatial layer" (what is
in frame) and a "temporal layer" (how it changes), so the prompt should address both:

> **precise subject + action details + scene/environment + lighting & colour tone + camera
> movement + visual style + image quality + constraints**

Their framing: a good prompt is *"not simply copywriting-style description, but an
engineering-style instruction"*. In practice that means concrete verbs and named camera
moves, not atmosphere words. ByteDance's own negative example is punished specifically for
*"the scene feels very cinematic"* — abstraction with no shot decomposition.

**Length: 40–200 words for a single shot, 150–330 for a multi-shot storyboard.** The API
allows 1000 but explicitly warns that long prompts scatter attention and drop elements. The
ceiling is not the target.

### One camera move per shot

The single most actionable rule ByteDance publishes, verbatim:

> Try to specify only 1 type of camera movement in a single shot. Do not require push, pull,
> pan, and move at the same time, as this will increase image instability.

If you need a compound move, split it across shots. And **always give a move an endpoint** —
"slow dolly-in from a medium two-shot to a tight single on her hands" — because a move with
no destination is where drift and smearing come from.

Be honest about the ceiling here: ByteDance's own technical report scores **advanced camera
movement as the model's weakest axis** (2.71, with no model above 3.14). Spend your control
budget on shot size and angle, which are well supported and cheap to specify, rather than on
elaborate choreography. If a specific move genuinely matters, supply a camera-movement
reference video rather than describing it.

### Multi-shot is the documented default for anything complex

Write a storyboard, not a paragraph. Per-shot slot order is official: **camera → action and
expression → space → audio.**

```
[Preamble: reference/asset binding, subject definitions, global style]

Shot 1: [camera move or shot size]. [Subject] [action + expression].
        [Position or spatial change]. [Audio].
Shot 2: The camera cuts to [shot size]. [Subject] [action]. [Space]. [Audio].
Shot 3: [camera move]. [Subject] [action]. The camera [final move] and freezes on
        [final composition]. [Audio].

[Trailer: global style, image quality, constraints]
```

That preamble/shots/trailer shape is the most transferable thing in the whole guide. Roughly
**3 shots per 8–12 seconds**.

If you *don't* want cuts, say so — "single continuous take, no cuts" — because a long action
description gets silently broken into shots otherwise.

### Keep camera and subject motion grammatically separate

Verbs like "moves right", "follows", "circles" and "rises" apply to both. Every official
example makes **"The camera"** the explicit subject of camera clauses and a named label the
subject of action clauses, in separate clauses. Never "we push in", never a bare participle.
Once more than one subject is in frame, never use a pronoun.

## Rules that hold across models

1. **Spend words on verbs, not adjectives.** Motion is what the model animates. "A flamenco
   dancer drops into a low spin, the skirt flaring wide before she snaps upright and stamps
   twice" beats any amount of "stunning, cinematic, 8k" — and those quality words actively
   push toward the generic AI-video look.
2. **Give physics a consequence to chase.** "Leaves scatter on each impact", "the mug slides
   and tips" — not "windy", "clumsy".
3. **Quantify motion.** Body part, range, speed, force. Seedance's docs explicitly prefer
   *"slow, gentle, coherent subtle movements"* over large dynamic action; big motion is where
   deformation appears.
4. **Positive phrasing everywhere except the trailer.** There is no negative-prompt field.
   Exclusions of *content* work poorly mid-prompt, but the constraint trailer genuinely parses
   literal negations — that is where ByteDance's own `Keep it subtitle-free` /
   `Do not generate a watermark` strings live.
5. **One clear action per shot.** Stacking actions is the other half of the instability
   problem that stacking camera moves causes.
6. **Assume you will iterate, and draft cheap.** You cannot see the result, so the first
   render is a question to the user, not a deliverable. 480p drafts cost pennies.
7. **Write prose or a shot list — not JSON.** Runway states it plainly: *"JSON prompts give
   the placebo effect of being more accurate… JSON formatting is ignored by generative models
   — what matters is the detail provided within the prompt."* The structure helps *you* not
   forget a slot; it does nothing for the model.
8. **When a clip melts, freeze the camera first.** Morphing subjects and unwanted camera drift
   are the same defect — these models *"struggle to distinguish between a camera moving and
   the actual world changing shape."* Pinning the camera reduces subject warping even when the
   camera didn't look like the problem.

## Two traps specific to this server

**The default model caps at 720p.** `CINEMAI_DEFAULT_VIDEO_MODEL` is
`bytedance/seedance-2.0-fast`, which supports only 480p and 720p. Asking it for 1080p is
rejected before spending — name `bytedance/seedance-2.0` when you need more.

**`aspect_ratio` defaults to `16:9` and is always sent.** As with images, that default is
applied even when you pass a reference image, so animating a 9:16 still without setting the
ratio reshapes it. When a reference supplies the framing, pass its ratio explicitly.
